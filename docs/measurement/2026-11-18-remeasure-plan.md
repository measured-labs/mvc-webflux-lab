# 재측정 계획 — MVC 일반 스레드 · MVC 가상 스레드 · WebFlux (2026-11-18, 측정 전 고정)

이 문서는 측정을 시작하기 전에 커밋으로 고정한다. 측정 뒤에 바꾼 것이 있으면 결과 문서에 따로 적는다.

## 왜 다시 재나

- 옛 결과(README "주요 발견")는 "Virtual Threads 덕분에 MVC도 높은 동시성"이라고 적었다. 그런데 저장소에는 가상 스레드를 켠 설정이 없다(앱 설정 · compose · 커밋 27개 모두). Spring Boot 4.0 기본값으로 띄우면 요청은 Tomcat 일반 스레드(`http-nio-*-exec-*`)에서 처리된다(2026-11-18 로컬 확인).
- MVC의 100ms 대기 엔드포인트가 실제로는 100µs만 잤다(`TimeUnit.MICROSECONDS.sleep`). 그래서 옛 결과의 "MVC 9.9ms · WebFlux 108ms"는 서로 다른 일을 잰 값이다. 커밋 eaa0a63에서 밀리초로 고쳤고, 고친 뒤 두 조건 모두 111~115ms에 응답한다.

## 조건

| 조건 | 앱 | 요청 처리 스레드 | 확인 방법 |
|---|---|---|---|
| MVC 일반 스레드 | mvc-app | Tomcat 스레드 풀(최대 200) · `VIRTUAL_THREADS=false` | 응답의 `thread`가 `Thread[...]` |
| MVC 가상 스레드 | mvc-app(같은 이미지) | 요청마다 가상 스레드 · `VIRTUAL_THREADS=true` | 응답의 `thread`가 `VirtualThread[...]` |
| WebFlux | webflux-app | Netty 이벤트 루프 | 해당 없음 |

- 같은 코드(커밋 고정), 같은 JVM 옵션(`-Xms512m -Xmx1024m`), 컨테이너 제한 CPU 2개 · 메모리 1G(원래 compose와 같음).
- 실행마다 컨테이너를 새로 띄운다. 한 번에 한 조건만 떠 있다(옛 측정은 두 앱이 같은 서버에 함께 떠 있었다).
- 앱 서버와 부하 발생 서버를 나눈다(앱 서버 16스레드 · 부하 발생 서버 6코어, 같은 LAN). nginx 프록시 없이 앱 포트를 직접 부른다.

## 시나리오

| 시나리오 | 파일 | 부하 | 보는 것 |
|---|---|---|---|
| load | `scenarios/load-test.js`(그대로) | 50 → 100 VU 10분, 요청 사이 0.5초 쉼 | 옛 결과와 같은 조건의 응답 시간 |
| stress | `scenarios/stress-test.js`(그대로) | 100 → 300 VU 10분, 요청 사이 0.1초 쉼 | 고부하 응답 시간 · 오류율 |
| pool | `scenarios/pool-test.js`(새로) | 100ms 대기만, 쉼 없이 100 · 400 · 800 · 1600 VU 각 2분 | 스레드 풀 포화 구간의 처리량 · p99 |

- 반복: 조건 × 시나리오마다 3회. 회차마다 조건 순서를 돌린다(`scripts/remeasure/run-campaign.sh`).
- 기록: k6 summary(JSON) 원본, 실행 로그, 조건 확인용 응답(`*.thread.json`)을 결과 폴더에 그대로 둔다.

## 가설 (측정 전)

- H1(pool): MVC 일반 스레드는 400 VU부터 처리량이 약 2,000 req/s(200 스레드 / 0.1초)에서 멈추고, p99가 VU 수에 비례해 늘어난다. MVC 가상 스레드와 WebFlux는 CPU 2개가 한계가 될 때까지 처리량이 더 오른다.
- H2(load · stress): 동시에 처리 중인 요청이 스레드 풀 200개보다 적어서, 세 조건의 차이가 작다(중앙값 기준 10% 안쪽).

## 읽는 법 (측정 전 고정)

- 조건별 값은 3회의 중앙값으로 비교한다. 3회의 범위가 겹치지 않을 때만 "차이가 있다"고 쓴다.
- 오류율이 1%를 넘는 실행은 그 단계의 지연 수치를 결론에 쓰지 않고 오류로만 적는다.
- 조건 확인 응답이 기대와 다르면(예: 가상 스레드 조건인데 `Thread[...]`) 그 실행은 무효로 하고 다시 잰다.
