## 질문

동시에 처리 중인 요청이 Tomcat 스레드 풀보다 많아지면, Spring MVC(일반 스레드 풀) · Spring MVC(가상 스레드) · Spring WebFlux의 처리량과 응답 시간은 어떻게 달라지나?

## 왜 다시 쟀나

첫 측정(ADR-000, 2025-12)의 결론은 두 가지 이유로 쓸 수 없었다.

- MVC의 100ms 대기 엔드포인트가 실제로는 100µs만 잤다(`TimeUnit.MICROSECONDS.sleep`). 그래서 "MVC 9.9ms · WebFlux 108ms"는 서로 다른 일을 잰 값이다. 커밋 eaa0a63에서 밀리초로 고쳤다.
- README는 "가상 스레드 덕분에 MVC도 높은 동시성"이라고 적었지만, 저장소에는 가상 스레드를 켠 설정이 없다(앱 설정 · compose · 커밋 기록 모두). 저장소 설정 그대로 띄우면 요청은 Tomcat 일반 스레드에서 처리된다.

## 조건

| 조건 | 요청 처리 방식 | 실행마다 확인한 것 |
|---|---|---|
| MVC 일반 스레드 | Tomcat 스레드 풀(최대 200) · `VIRTUAL_THREADS=false` | 요청을 처리한 스레드 이름 `Thread[...http-nio-...]` |
| MVC 가상 스레드 | 요청마다 가상 스레드 · `VIRTUAL_THREADS=true`(같은 이미지) | 스레드 이름 `VirtualThread[...tomcat-handler...]` |
| WebFlux | Netty 이벤트 루프 · 대기는 `Mono.delay` | 응답의 서버 종류 `WebFlux-Netty`(응답 스레드 이름은 `Mono.delay`를 실행한 Reactor `parallel` 스레드라 이벤트 루프 확인에는 쓰지 않음) |

- 코드 커밋 cea1db5의 jar · Spring Boot 4.0 · Java 25 · 컨테이너 CPU 2개 · 메모리 1G · JVM `-Xms512m -Xmx1024m` · 실행마다 컨테이너를 새로 띄우고 한 번에 한 조건만 띄움.
- 앱 서버(16스레드)와 부하 발생 서버(k6 1.4.2)를 나눔 · 같은 LAN · 프록시 없이 앱 포트 직접 호출. 조건 확인은 컨테이너를 띄운 직후 요청 1번으로 했다(부하 중에는 확인하지 않음).
- 시나리오 3개 × 조건 3개 × 3회 = 27회. 회차마다 조건 순서를 돌림.

## 무효 실행과 다시 재기

측정 중 앱 서버와 부하 발생 서버 사이 연결이 약 37분마다 20초 안팎으로 끊겼다. 처음 27회 가운데 7회가 끊김에 걸렸다(로그의 `network is unreachable` 또는 최대 응답 26~33초). 보완 계획의 기준(로그에 `network is unreachable`이 있거나 최대 응답이 10초를 넘으면 무효)을 27회 모두에 같게 적용해 정확히 7회를 무효로 하고, 같은 회차 · 조건 · 시나리오로 다시 쟀다.

- 다시 잴 때는 부하 발생 서버를 바꿨다(처음 .158 → 다시 잰 7회 .9). 그런데 부하 발생 서버를 바꾼 뒤에도 같은 주기의 끊김이 4번 더 걸렸다(`rerun/rerun-1.log` 3번 · `rerun/rerun.log` 1번). 끊김의 원인은 부하 발생 서버가 아니라 앱 서버 쪽이나 그 사이 네트워크로 보인다(원인은 확인하지 않았다).
- 다시 재기 도구는 실행마다 끊김을 검사해 무효면 그 실행만 다시 잰다. 결과에 쓴 27회(처음 측정 20회 + 다시 잰 7회) 중 무효 기준에 걸린 것은 없다. 유효한 실행의 최대 응답은 모두 3초 이하였다.
- 어느 실행이 처음 측정이고 어느 실행이 다시 잰 것인지는 `SUMMARY.md` 끝의 표에 있다.
- 다시 재는 동안 도구 버그(실행 이름에서 조건을 잘못 잘라 WebFlux 컨테이너를 띄우지 않음)로 WebFlux 2회가 두 번 실행되지 않았다. 고친 뒤(커밋 4104242) 다시 쟀다. 무효 시도의 로그는 재시도 때 덮어써져 남지 않았고, 시각만 `rerun/rerun-*.log`에 있다.

## 가설 판정 (측정 전 고정한 읽는 법)

- **H1 맞음**: MVC 일반 스레드는 400 VU부터 1600 VU까지 처리량이 약 2,000 req/s(이론 상한 200 스레드 ÷ 0.1초)에서 더 오르지 않았다(1,987 · 1,992 · 1,999). p99는 VU에 비례해 213 → 422 → 830ms로 늘었다. MVC 가상 스레드와 WebFlux는 1600 VU까지 처리량이 계속 올랐다. 400 VU 이상에서 세 조건의 3회 범위는 서로 겹치지 않는다. 가설의 "CPU 2개가 한계가 될 때까지"는 확인하지 못했다(측정 중 CPU 사용률을 기록하지 않음).
- **H2 맞음(처리량 · 전체 p95 기준)**: load · stress에서 세 조건의 처리량과 전체 요청 p95 차이는 중앙값 기준 1% 안쪽이었다(stress 1,655.3 ~ 1,667.9 req/s). 다만 엔드포인트별로 보면 load의 CPU 계산 엔드포인트 p95는 WebFlux 3.5ms · MVC 일반 스레드 4.0ms · MVC 가상 스레드 4.7ms로 차이가 있고 범위도 겹치지 않는다(수 ms 단위라 결론에는 쓰지 않음). 요청 사이에 쉼이 있어 동시에 처리 중인 요청이 스레드 풀 200개를 채우지 못하기 때문이다.

## 결론

- 대기가 긴 요청이 스레드 풀보다 많이 동시에 들어오면, 일반 스레드 풀의 MVC는 "스레드 수 ÷ 대기 시간"(이 측정에서 약 2,000 req/s)에서 처리량이 멈추고 응답 시간이 대기열만큼 늘어난다. 같은 코드에 가상 스레드를 켜는 것만으로 1600 VU 처리량이 약 5.4배(1,999 → 10,876 req/s)가 됐다.
- 같은 조건에서 WebFlux는 처리량(15,002 req/s)과 p99(146ms) 모두 가상 스레드보다 좋았다. 이 측정 범위(최대 1600 VU · CPU 2개 · 인공 대기)에서 가상 스레드는 일반 스레드 풀의 약 2,000 req/s 정체를 넘었지만 WebFlux에는 못 미쳤다.
- 요청 사이 쉼이 있는 일반 부하(load · stress)에서는 세 방식의 처리량 · 전체 p95 차이가 1% 안쪽이었다. 동시성 모델의 차이는 동시에 기다리는 요청이 스레드 수를 넘을 때 드러난다.

## 한계

- 대기 엔드포인트는 `Thread.sleep` · `Mono.delay`의 인공 대기다. DB · 외부 호출처럼 커넥션 풀이 함께 막히는 경우는 재지 않았다.
- 측정 중 CPU · 메모리 사용률을 기록하지 않았다(`*.stats`는 실행이 끝난 뒤 한 번 찍은 값). 가상 스레드와 WebFlux의 차이가 CPU에서 생겼는지는 알 수 없다.
- 부하 발생 서버의 NIC는 100Mbps다. WebFlux 1600 VU(약 15,000 req/s)에서 응답 약 253바이트 · 요청 약 89바이트로 계산하면 수신 약 30Mbps · 송신 약 11Mbps라 한계(100Mbps)의 약 40%다. 다만 이 계산에는 TCP · HTTP 헤더 일부가 빠져 있다.
- 다시 잰 7회는 다른 부하 발생 서버(.9 · 8스레드)에서 쟀다. 같은 칸 안의 처음 측정과 다시 잰 값의 차이는 대부분 1% 안쪽이었다. 예외는 둘이다. MVC 일반 스레드 pool 100 VU(처음 측정 923 req/s · 다시 잰 871 · 866 req/s — 컨테이너를 띄운 직후의 첫 단계라 준비 시간의 영향을 받는 단계)와 WebFlux pool 1600 VU로, 다시 잰 2회차가 14,580 req/s로 처음 측정한 1회차(15,002) · 3회차(15,033)보다 약 3% 낮았다(부하 발생 서버의 처리 한계에 가까웠을 수 있음 — 확인하지 않음). 중앙값(15,002)은 처음 측정 값이다.
- 끊김의 원인은 확인하지 않았다. 끊김을 실행마다 검사해 걸러냈지만, 걸러내는 기준(최대 응답 10초) 아래의 짧은 끊김이 섞였을 가능성은 남는다.
